## The one rule that matters

Prisma connects as the database owner — `postgres`, which has
`rolbypassrls = true` — so it **bypasses RLS entirely**. The `where` clause is
the tenant boundary, full stop. Every query is scoped by `userId`; a forgotten
one leaks another carrier's data and returns no error. Prefer
`lib/crudService.ts` helpers, which force `userId` and throw 403 on a
cross-tenant filter. Cross-tenant ids should 404, not 403.

RLS is therefore not protecting application code. It protects anon-key clients.
That distinction matters: RLS being correct is necessary, and still not sufficient.

## Environment traps that have actually cost time

- `connect_timeout=30` is required on both database URLs. Prisma's 5s default
  is below the 2.4–11.6s cold TLS handshake on this network and produces
  `P1001: Can't reach database server` on a healthy host. Next.js's error advice
  blames the port; the port is not the variable.
- Stop all node processes before `prisma generate` or the Windows DLL stays
  locked (`EPERM ... rename`).
- If you see `EINVAL: invalid argument, readlink '.next\...'`, that is OneDrive
  evicting the build dir, not a corrupt build. `Remove-Item .next -Recurse -Force`,
  then `attrib +P -U /S /D .next`.
- Never paste a real credential into a tracked file. `.env.example` is tracked
  and must stay empty; `npm run verify:secrets` runs in CI and has caught a leak
  already.
- `SUPABASE_SERVICE_ROLE_KEY` and `GEMINI_API_KEY` are unset, so Storage,
  inbound email and AI extraction are untested against their providers.

## How to work

Measure, don't speculate. When something is intermittent, run enough attempts to
report real numbers and the method — a 15-per-port comparison is what proved
the port was a red herring. Separate *latent* defects from *active* ones and say
which. Verify before you claim: a subagent asserted `POST /api/loads` "500s on
every call", and checking `pg_attribute.attgenerated` showed the column is not
generated today, so it is latent, not active.

Prove a fix is not the fix. A check that cannot fail is not a check: after
adding an RLS coverage guard, delete the entry it protects and confirm the suite
goes red before trusting it. Equally, when a change seems to break something,
isolate it before believing it — a failing live test after a schema migration
turned out to be a `connection_limit=1` pool timeout, not a permissions break.

Prefer fixing a root cause over adding a retry. Do not claim a feature works
until you have run something that proves it — returning 200 from `/pricing` or
`/login` proves nothing, because neither page touches the database, and
`/dashboard` redirects before querying.

Keep changes scoped and verifiable. Run `npm run typecheck`, `npm run lint` and
the relevant `verify:*` script before reporting done, and say which ones you ran.
